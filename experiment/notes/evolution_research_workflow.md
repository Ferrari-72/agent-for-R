# 张量网络代码进化：研究流程与经验反馈协议

状态：实验设计基线，2026-10-23。本文定义后续实验如何判断成功、分类失败、总结经验和验证反馈机制。它不是算法效果报告，也不授权真实模型请求。每次实际运行仍须另存预注册表、固定预算和明确审批。

## 1. 研究目标与成功定义

研究目标不是让模型生成一段看起来合理的收缩算法，而是检验：在固定接口、数据、评估器和资源限制下，代码进化系统能否稳定地产生**合法、确定、独立复核通过且在未参与搜索的数据上优于预先指定基线**的收缩路径。

成功必须分层报告，不以单一最高分代替：

1. **协议正确**：冻结的候选接口、动态位置路径规则、收缩列表更新规则和数据版本均满足；评估器对非法路径拒绝，候选无法自报或覆盖可信指标。
2. **可重复**：同一候选、实例和 seed 重复返回同一路径；路径、代价、峰值和汇总均能由独立代码复算。时间只有在原 runner、依赖和环境被归档且重放时才声称可复现。
3. **搜索有效**：预注册的开发集主指标相对固定对照达到预设阈值，同时满足合法率、超时率、峰值和请求预算约束。所有候选失败均计入分母，不只汇报最佳候选。
4. **跨运行稳定**：通过预先规定数量的独立运行评估运行间差异。单次运行、多轮迭代或多个实例都不能代替独立运行。
5. **泛化**：候选、prompt、规则和分析方案冻结后，才能评估最终集/迁移集。保留集结果不回流搜索、prompt、经验库或候选；若回流，必须登记新协议并更换未触碰的评估集。

报告至少列出：候选尝试和接纳数、合法/确定/通过开发集比例、主指标及逐例分布、相对 Greedy 和预先定义强基线的比值、资源和请求开销、独立运行数、失败分类、协议偏差及证据完整度。算法改进结论要区分点估计、跨运行不确定性和 held-out 结果。

## 2. 全流程与阶段门

| 阶段 | 工作 | 进入下一阶段的门槛 | 必留证据 |
| --- | --- | --- | --- |
| A. 规格与基线 | 固定任务接口、合法路径、代价、峰值、时间、失败语义；复核已有基线 | 独立 scorer 测试通过；开发集和保留集清单/哈希齐全 | 任务规格、基线代码/路径/报告、数据清单 |
| B. 环境冻结 | 冻结 prompt、配置、代码、依赖、runner 镜像、数据、预算数据库身份 | 快照和哈希可核验；正式预算库已存在且余量经核对；镜像归档可读 | 源码快照、manifest、镜像 tar/hash、lockfile、预算库路径和起止位置 |
| C. 评估链校准 | 用构造的有效/无效程序校验 parser、sandbox、错误分类、重复性、计时、报告和续跑 | 所有预期接受/拒绝结果正确；不消耗真实 API 额度 | 合成候选、输入、预期结果、测试输出 |
| D. 模型能力校准 | 在不搜索最终/迁移集的前提下，测模型是否能遵守格式、读取 API 合同、修复简单受控错误 | 校准题和判分规则预先固定；请求预算独立登记；表现不足时标为模型/接口能力限制 | 校准 prompt/响应、模型版本、token、请求增量、错误标签 |
| E. 预注册消融 | 每次登记一个主要变量和一个明确对照，固定模型、候选、数据、预算、评估预算和运行次数 | 可证伪假设、主要指标、样本量、停止规则和偏差处理先写好 | 运行登记表、冻结 hash、对照关系 |
| F. 开发集搜索 | 按预注册协议运行，保存逐轮原始证据；只允许开发集反馈 | journal、prompt、响应、候选、阶段结果、预算计数完整；报告独立复核一致 | 每轮 prompt/response/source diff/artifact、请求/成本/时间日志 |
| G. 经验整理 | 抽取事实、形成假设、评估证据等级，不能自动把单例归纳成普遍规则 | 每条经验有来源、适用范围、验证状态和反例检查 | 版本化经验记录及来源链接 |
| H. 独立审查与重放 | 审核者只读挑战成功判据、泄漏、归因和快照；另一环境校验镜像/依赖 | 高严重度发现关闭或明确接受；重放差异有解释 | 审查 findings、修复/偏差记录、重放日志 |
| I. 冻结与保留集 | 冻结候选和协议；一次性评估最终/迁移集 | 无未决代码/协议变化；数据访问隔离和一次性标记生效 | 最终代码/规则 hash、逐例报告、访问审计 |
| J. 综合结论 | 综合独立运行、失败、预算和保留集，不夸大证据 | 结论明确支持/不支持/不确定及其适用范围 | 研究报告、可复算产物、历史请求账本 |

阶段失败时保留已产生证据并停止推进；修复后需判断是否仍是同一协议。改变模型、prompt、候选接口、预算、评估器或数据均可能构成新协议，不能静默续跑并合并计数。

## 3. 错误分类与归因边界

日志先记录**观察到的错误类别**，再记录**可能原因假设**。单凭一次失败不能确定因果，也不能把无法解释的错误自动归咎于候选算法。

| 观察类别 | 示例 | 可直接确认的事实 | 不可直接下的结论 |
| --- | --- | --- | --- |
| 请求/服务 | 认证失败、限流、超时、服务端错误 | HTTP 状态、请求 ID、发生阶段、是否计入预算 | 候选算法差或模型能力弱 |
| 输出协议 | 无 diff、delimiter 错、额外文本、多块违规 | 原始响应与 parser 结果 | 模型总体不能编程 |
| API/知识 | 错参数、调用不存在的 API | traceback、锁定版本、对应 API 合同 | 算法思路无效 |
| 语法/接口 | SyntaxError、缺少 `find_path`、签名不兼容 | 解析/接口检查结果 | 搜索策略无效 |
| 路径语义 | 长度、索引或动态列表更新非法 | validator 反例与输入 | 单纯“模型太弱”；需查提示和协议难度 |
| 运行资源 | 超时、内存/峰值超限 | 可信父进程计时、资源监控值 | 路径质量差；需区分搜索预算与候选失控 |
| 非确定性 | 相同输入和 seed 路径不同 | 重复运行的路径差异 | 平均分较差；它是独立的可重复性失败 |
| 目标退化 | 路径合法但代价更高 | 独立 scorer 的逐例代价 | 模型失败；这可能是有效但不好的算法提案 |
| 证据/协议失效 | prompt/hash 缺失、预算库不明、快照不匹配 | 缺失/冲突的 artifact | 仍可把运行作为正式实验纳入汇总 |

### 模型能力校准

“模型太弱”是合理解释，但必须通过独立校准支持，不是失败后的兜底说法。校准需在搜索前固定一组小任务：严格 diff 格式遵循、已知 API 合同问答/代码调用、简单路径合法性、已知局部优化和对照修复。判分由机器 validator 或预先写定的答案检查，不用模型自评。

校准结果用于描述当前 model × prompt × task 的能力边界。若模型连协议格式或简单受控题都无法稳定通过，主实验应标为**模型接入/能力不足导致信息量有限**，而非据此判定整个进化方法无效。若格式/API 校准通过但候选算法无改善，才把结论收窄到该搜索配置未显示改善。弱模型结果仍是有效的特定模型实验，但不得外推到更强模型或一般 Agent 能力。

校准本身会消耗真实请求，因此必须有单独登记、预算额度和请求计数；不得借助新数据库绕过既有预算限制。没有获批额度时，只运行 mock、静态和本地合成测试。

## 4. 反馈与经验利用方案

所有方案都使用同一 correctness gate：模型建议只能变成候选；候选必须通过 parser、语法/接口、sandbox、路径 validator、三次确定性检查、完整开发集评分和独立 scorer。反馈和经验不改变裁判标准。

| 方案 | 输入模型的反馈 | 好处 | 风险/适用性 | 优先级 |
| --- | --- | --- | --- | --- |
| F0 无历史反馈 | 当前代码、指标和任务规则 | 最干净的对照 | 不能学到近期错误；必须作为基线 | 必需控制 |
| F1 简洁失败摘要 | 错误阶段、分类、关键异常行 | token 少，能测试错误反馈本身的价值 | 诊断上下文不足 | 第一轮 treatment |
| F2 结构化失败记录 | case、seed、阶段、错误码、期望/实际、复现标记 | 可审计、易聚类、方便统计错误率 | schema 和 prompt token 增长 | 第一轮 treatment |
| F3 最小反例 | 失败实例和最小重现步骤，不给保留集 | 对动态索引/边界错误有针对性 | 反例缩减可能改变问题；只从开发数据生成 | 后续 |
| F4 成功/失败逐例对照 | 父代与候选的路径、代价、峰值变化 | 便于识别回归和规模敏感性 | 多因素变化时难作因果解释 | 后续 |
| F5 已验证经验检索 | 检索少量、有来源且通过重复验证的条目 | 可能减少重复错误 | 陈旧、错误泛化、经验泄漏 | 第二阶段研究 |
| F6 lineage/history | 最近若干代 prompt/代码/反馈 | 保留搜索轨迹，可能避免重复尝试 | 上下文膨胀、局部路径依赖 | 单独消融 |
| F7 inspiration programs | 一个或多个已评估代码及指标 | 展示算法空间的具体例子 | 参考不等于 parent；可能复制失败方案 | 单独消融 |
| F8 模型自我反思 | 要求模型解释失败并提出方案 | 可能产生新假设 | 自述可能编造原因，形成自我强化偏差 | 最后研究；仅作为假设 |
| F9 人工审核经验 | 研究者审核后提供 API/语义规则 | 适合硬事实和 API 陷阱 | 人工成本、维护和选择偏差 | 硬约束渠道 |

不应一次性合并多种反馈。第一轮只比较 F0、F1、F2；之后才检验 F3/F5/F6 等。一次 treatment 同时改变反馈详细度、历史长度和 inspirations 时，结果不可归因。

## 5. 经验记录格式与晋级规则

经验库是有证据的研究数据，不是自由文本记忆。每条记录最少包含：

```yaml
experience_id: stable-id
status: hypothesis | single_run | replicated | contradicted | retired
scope:
  failure_class: observed category
  input_size_or_shape: explicit range or unknown
  model_and_version: exact identifier
observation: directly observed event
interpretation: separated fact from causal hypothesis
recommendation: one testable next action
source:
  run_id: exact run
  iteration: integer
  case: exact case or null
  prompt_response_artifact: relative path and hash
  candidate_sha256: hash or null
counterexamples: list or empty
validation_runs: list of independent runs
last_reviewed: date
```

晋级规则：

- 单次观察只进入 `single_run` 或 `hypothesis`，不得作为确定规则注入 system prompt。
- 硬事实（接口签名、validator 规则、锁定 API 行为）须链接到源码、测试或受控复现；优先放进测试/约束，不以经验文本替代代码保护。
- 可操作的经验规律至少需预先定义的重复验证；登记中明确重复次数和成功标准。相关性不得写成因果。
- 被反例推翻时保留原条目并标 `contradicted`，不可删除历史或静默改写。
- 每次经验检索都记录被检索条目 ID、版本、排序、注入 prompt 的确切内容/hash、token 占用和适用性判断。
- 最终集/迁移集结果永不进入搜索经验库；发现污染则当前 held-out 结论失效。

## 6. 建议的验证顺序

1. **本地正确性校准**：用 mock 造出协议错误、错 API、语法/接口错误、非法路径、超时、非确定性、合法但退化、预算耗尽和快照篡改；逐项检查错误分类、拒绝行为、原始证据和下一轮反馈。此阶段零 API 请求。
2. **模型接入校准**：只有在预算审批和计数确认后，固定小型能力套件，估计当前模型对 diff、接口/API、简单合法路径的通过率。先写判定阈值，失败仅描述为模型/提示组合表现不足。
3. **F0/F1/F2 消融**：固定模型、初始代码、seed、实例、iteration 上限、评估和请求上限；按预注册安排独立运行。主结果先比较协议成功率、合法率、评估成功率和错误结构，再比较开发集代价。
4. **经验检索消融**：只有 F1/F2 证明反馈有可重复价值后，比较无经验检索与只检索 replicated 条目；冻结经验库版本，按条目 ID 记录曝光。
5. **更复杂上下文**：分别研究最小反例、history、inspirations、反思或 crossover；一个实验一个变量。
6. **最终/迁移评估**：只在候选和实验协议冻结后运行。开发集方案选择不得查看该结果；新协议需使用新的保留集。

每个真实实验都需记录计划的独立运行数、实际运行数和为何停止。请求预算耗尽、服务故障或模型连续协议失败按预注册停止规则处理；不得通过换预算库延长一项实验。预算数据库累计数、本次运行起止位置和本次新增数分别报告。

## 7. 下一步工作清单

### 必做，真实模型运行前

- [ ] 更新预注册模板，增加模型校准、失败类别、独立运行数、请求数据库身份/起点/额度、镜像归档和经验库版本字段。
- [ ] 加本地合成失败分类测试，验证 observation 与 causal hypothesis 分开存储。
- [ ] 加经验记录 schema 校验和经验状态晋级规则；禁止未经审核的模型反思自动成为硬规则。
- [ ] 复核正式运行脚本是否在调用模型前校验请求库路径、历史累计数、限额、镜像、快照和预注册表。
- [ ] 由独立审核者检查协议、隔离、报告措辞和测试覆盖；修复后复审。
- [ ] 核准一个明确的新请求预算与唯一预算数据库；如果未核准，仅运行本地测试。

### 第一轮研究问题

- 问题：结构化失败反馈是否比不提供历史反馈提高弱模型的候选协议成功率/开发集有效候选率？
- Treatment：F2 结构化失败反馈。
- Control：F0 无历史反馈；F1 简洁摘要作为中间机制对照。
- 固定：模型精确版本、模型参数、初始程序、prompt 主体、数据/seed、OpenEvolve 选择机制、最大轮数、每候选评估预算、总请求预算和独立运行数。
- 主要结果：协议有效候选率与开发集完整评估有效候选率；不得只比较最佳单轮分数。
- 次要结果：失败类别分布、重复失败比例、每个有效候选的请求/token 成本、开发集代价分布。
- 假设：F2 降低可由明确失败原因修复的协议/API/路径错误；若格式/API 校准不足，结果先归为模型接入表现不足，不推断反馈设计无效。
- 判定：运行数不足、预算不足或日志缺失时结论为不确定；统计判定阈值和实际运行数必须在执行前填入登记表，不以看到结果后选择阈值。

## 8. 明确不做的事

- 不因“弱模型也许做不到”而放宽正确性、路径验证或复现要求。
- 不把格式错误、API 幻觉、算法退化、服务失败和评估器缺陷混成一个失败标签。
- 不把模型自述原因写成已证实根因。
- 不把多个 prompt 参考程序叫作多个遗传父代。
- 不在一个实验里同时加入失败反馈、经验检索、history、inspiration 和 crossover。
- 不删改历史请求数据库、旧报告或失败 artifact 来美化预算与结果。
- 不用最终集/迁移集选择 prompt、经验条目、候选或阈值。
- 不因已有一条路径分数改善就声称整个算法稳定有效；保存数值独立复算也不等于重现旧执行过程。
