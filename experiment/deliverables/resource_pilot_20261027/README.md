# Public engineering resource pretrial

This DECOUPLED pretrial fixes and exposes the complete 12-case structure-only pool before any solver starts. It contains eight qubit-circuit fixtures (q8/q12 at depth 4/8, two each) and four connected square-lattice fixtures (4x4/5x5, two each). Admission uses bounded `tnlab.structure_equivalence.compare_structures`; a timeout or `unknown` comparison stops pool preparation without substitutions. Generation is finite (32 attempts per cell). Solver results cannot change pool membership.

The run executes three teacher routes (`partition`, `tree`, `beam`) and four baselines (`greedy`, `random-greedy`, `simulated-annealing`, `omeco`), with two rows per solver and fixture (168 expected rows). Candidate routes use seed 0 and their two returned paths must match. Baseline repeat labels are retained, but are not presented as repeatability guarantees; OMECO receives `seed=None` because its adapter has no caller seed API. Every valid path receives `tnlab.scoring.score_path` plus a separate set-based cost/peak simulation.

All topology, equivalence, solvers, and scoring run in the pinned Linux Docker image `sha256:ad059619f459c42aded047c343847fc4fc7fd9e025b3993b687768c9f549d5b3` with source label `008592ed6a4dc8291f5de6f7719799bfe839b0758170bfbc7f8aac494979c763`, one CPU, 2 GiB memory, 64 pids, no network, read-only root, and uid 65534. The Windows host only stages files and starts Docker. Per-solver and per-score process wall budgets are 10 seconds; failures stay in the full denominator.

Run `python -I E:/张量网络/experiment/deliverables/resource_pilot_20261027/run_resource_pilot.py` on the host. The launcher stages only public helper/source files in a unique `.tmp` directory, runs `pilot.py --prepare`, records the pool file hash, then runs `pilot.py --run`. `resource_spec.json` pins the independent specification, `pool_preparation.py` owns pool admission/tests, `solver_worker.py` owns solver/scorer calls, and `pilot.py` owns Linux orchestration. The host performs image/source/hash metadata checks only. Raw evidence is retained in the unique directory named by `summary.json.evidence_directory`, including source manifest, invocation/process records, pool preparation, every worker request/response/stdout/stderr, and `rows.jsonl`.

`summary.json` is the machine-readable result. Each row records solver and scoring timings separately, process wall time, cost, peak elements, and RSS. RSS is `ru_maxrss` high-water RSS for the fresh worker process; imports/runtime startup are included, and it is not an incremental solver-only allocation measure. Teacher path repeat equality is checked per fixture; baseline repeats are not mislabeled as reproducible.

In this run, all seven solvers completed 24/24 rows with no 10-second timeout. Maximum observed solver process wall was 1.73s (OMECO); maximum score process wall was 0.73s. The greatest worker `ru_maxrss` was about 44 MiB (OMECO), against the 2 GiB container cap. Maximum symbolic peak was 33,554,432 elements. A 10s per-call wall cap and 1 CPU/2 GiB ceiling comfortably covered this fixture/parameter set; treat that as a starting cap for a similarly narrow public pretrial, not production sizing. OMECO's full default TreeSA adapter was the dominant measured solver cost at about 0.62s median algorithm wall. Score the solver path independently and retain score time/RSS separately when budgeting. These measurements are single-host; RSS includes imports and peak elements are not allocated RAM.

The pool is public and deliberately engineering-only. No model calls, formal research sample, held-out evaluation, historical corpus, final evaluation, or transfer data is used. These observations do not support unseen-performance, novelty, or research-efficacy claims.

## Implications for the proposed study

Retain the proposed 10-second solver and independent-score limits, with 1 CPU and a 2 GiB memory-plus-swap ceiling, for the next bounded engineering stage. Do not reduce limits to the fastest observed run or extrapolate a production completion time from these timings. The tested circuits contain 18–47 tensors with 8 or 12 output legs; the lattices contain 16 or 25 tensors with one output leg per site. The proposed q16/q20 circuit cells require their own resource evidence. The current proposed lattice sizes remain 4x4/5x5; 6x6 would be an additional, unbudgeted design change, not an implicit next task. The prototype's 256-input interface limit is not a calibrated workload size.

The beam route explored complete states but retained its initial incumbent on 5 of the 12 distinct structures (10 of 24 repeat rows): one 12-qubit/depth-8 circuit and all four lattice fixtures. Keep those rows and the generation-zero comparison. This diagnostic does not mean a failure, does not measure novelty, and is not a reason to change the frozen public pool or silently retune one route after seeing scores.
