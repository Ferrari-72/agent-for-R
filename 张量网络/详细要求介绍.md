# 项目介绍

## 问题

张量网络的收缩顺序会显著影响计算代价。同一个网络可以有许多合法顺序；找到低代价顺序通常需要启发式搜索。

本项目考察：**LLM Coding Agent 能否通过编写和反复修改搜索算法，在电路和格点张量网络上找到比现有基线更好的收缩顺序？** 这是原始题目 *Can an AI Agent Discover Better Tensor-Network Contraction Orders?* 的核心问题。

## 优化对象

设 `G` 是张量网络，`H` 是搜索算法，`π = H(G)` 是算法返回的收缩顺序，`C(G, π)` 是统一评估器计算的代价。

Agent 修改的是 `H`，不是直接为一个固定的 `G` 填写答案。单个实例可用于验证流程；要评价算法是否可复用，必须在多个网络上测试。

## 系统边界

1. **网络实例**：固定输入格式、拓扑、维度和生成种子。初期使用少量电路与格点实例。
2. **候选算法**：接收网络、随机种子和搜索时间预算，返回约定格式的收缩顺序。
3. **执行器**：在规定时间内运行候选，记录异常、超时和实际搜索时间。
4. **独立评估器**：检查顺序是否合法，按固定规则计算收缩代价。候选代码不能提供自己的分数，也不能修改评估规则。
5. **搜索循环**：将有效结果和错误反馈给 Agent，保存每轮代码、配置和评估记录，只按事先确定的规则选择候选。

“精确计分”指对**给定顺序**按固定规则计算代价，不表示评估器找到了全局最优顺序。FLOPs 的具体计数约定及所用工具版本，须在首次实验前固定并写入配置。

## 如何比较

- **主要指标**：同一实例上候选算法与基线的收缩代价之比。跨实例汇总时使用这些比值的几何平均，并保留逐实例结果。
- **独立指标**：算法找路径的时间、Agent 调用次数和消耗。收缩代价低但搜索时间极长，不应只凭一个分数称为更好。
- **公平条件**：相同实例、代价定义、随机种子方案和搜索时间预算。随机算法需要重复运行并报告波动。
- **泛化检查**：训练实例可用于迭代反馈；最终测试实例不用于提示、选择或调参。反复查看测试分数会使它失去独立性。

最小版本先比较 Greedy。研究阶段还需加入更强的人工搜索基线，避免只战胜弱基线就得出过大的结论。

## 阶段目标

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| 1. 评估基础 | 固定实例、候选接口、评估器、Greedy 基线 | 已知小例子的路径合法性和代价可验证 |
| 2. 自动迭代 | 生成、执行、反馈、选择和记录 | 连续运行 5–10 轮；成功与失败都可复查 |
| 3. 实验比较 | 更强基线、独立测试集、多随机种子结果 | 可区分训练改进与测试泛化，并报告搜索成本 |

首个可运行版本的目标是证明流程可信、可复现。是否发现有竞争力的新算法，需要第三阶段的对照实验来判断。

## 后续研究问题

基础流程跑通后，优先选择一个问题深入研究，而不是同时优化所有指标：

- **反馈利用**：只提供当前最优结果、提供最近几轮记录，或总结失败原因，哪种方式更有效？
- **搜索策略**：围绕当前最优算法修改，还是同时保留不同候选，能否在相同预算下找到更好的算法？
- **泛化与成本**：训练实例上的改进能否迁移到新网络？达到同等质量需要多少模型调用、评估次数和时间？

这些问题需要对照实验。单次运行结果只能说明该次实验的表现。

## 实施注意

限时子进程可以处理候选代码卡住或崩溃，但不等于安全沙箱。如果要把评估器称为严格“封闭”，候选执行环境还需隔离文件、网络和最终测试数据。原型阶段应明确记录这一限制。
