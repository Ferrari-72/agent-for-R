# 张量网络收缩顺序实验：任务拆解、设计与当前进展

阶段记录：2026 年 10 月 21 日。

## 我如何拆解原题

原题希望用 Coding Agent 发现更好的张量网络收缩顺序算法。我把它拆成两个需要分别验证的问题：**给定算法的路径能否被可信地评估**，以及 **Agent 能否通过反复修改算法取得可复现的改进**。Agent 编写的是对不同网络都可调用的搜索函数 `H`；它对网络 `G` 返回路径 `π=H(G)`。项目要比较的是 `H`，不是让模型记住某一个网络的答案。

据此，我按依赖关系安排五个阶段：①确定指标和候选接口；②固定实例并验证评估器；③运行人工启发式基线；④选择并适配开源 Coding Agent 框架；⑤接入真实模型，检查生成、执行、反馈和记录。前四项为第五项提供可信的输入。流程跑通后，再做相同预算、多随机种子和独立测试集的正式比较。下文区分**已验证**、**已实现但待真实复核**和**尚未完成**。

## 1. 指标：`R` 具体是什么

**已实现最小版本。** 对实例 `i`，令 `C_i(H)` 为候选算法给出的路径代价，`C_i(Greedy)` 为同一实例上 Greedy 路径的代价。定义 `r_i=C_i(H)/C_i(Greedy)`，主指标为所有有效实例的几何平均：

`R = exp((1/N) × Σ_i log(r_i))`。

例如两个实例的比值为 `0.8` 和 `0.5`，则 `R=√(0.8×0.5)≈0.632`。`R<1` 表示平均相对代价低于 Greedy，`R=1` 表示持平。它不是“正确率”，也不说明路径已达到全局最优。几何平均适合汇总跨实例的倍数变化；正式报告仍须列出每例的原始代价、比值和失败情况。OpenEvolve 内部用 `-log(R)` 转成“越大越好”的分数；只要有一个开发实例失败，就不给该候选定义有效的 `R`，内部固定记为 `-10`。当前只有四个开发实例，每例只运行固定种子；尚未形成多种子统计。

路径搜索耗时、最大中间张量元素数、失败率及模型调用成本单列，不与 `R` 混成一个数。当前候选每例最多运行 10 秒，最大中间张量为 `2^20` 个元素。这是原型的可行性限制；正式比较还要统一各方法的找路径预算。

### 为什么用 cotengra 计分

我选 `cotengra==0.8.3`，因为它能从**指定路径**重建 `ContractionTree`，计算该路径的 `contraction_cost()` 和最大中间张量大小。Greedy、Random-Greedy、模拟退火和 Agent 候选都交给同一函数计分，避免各算法自报分数或混用不同库的运算计数约定。评估时调用 `from_path(..., check=True, autocomplete=False)`；评估器先独立检查路径步数及每一步的位置，再禁止库自动补全。此处 cotengra **只评价给定路径**，不替候选寻找更优路径。[cotengra 路径与代价接口](https://cotengra.readthedocs.io/en/stable/autoapi/cotengra/core/index.html)

`contraction_cost()` 是按库约定计算的标量运算代价估计，不等于实际运行时间，也不能证明理论最优。为了核对计数，我对三张量链手工计算了两条路径，得到 64 和 90；又对该小例子的所有首步选择做了独立计算与库结果比对。版本已固定；若以后更换代价定义，旧结果不能直接合并。

## 2. 固定实例与评估器：如何确认实例正确

**六个最小实例已建立并通过当前检查。** 开发集有两个格点网络和两个量子电路网络；保留集有一个格点网络和一个电路网络。格点用 `cotengra.utils.lattice_equation` 生成；电路用 `quimb.tensor.circ_ansatz_1D_brickwork` 生成，并取其完整态张量网络。参数、种子、张量指标、输出指标和维度写入固定 JSON。这里优化的是网络的**收缩顺序**，与具体张量元素的数值无关。[cotengra 格点示例](https://cotengra.readthedocs.io/en/stable/advanced.html) · [quimb 电路生成器](https://quimb.readthedocs.io/en/latest/autoapi/quimb/tensor/circuit_gen/index.html)

正确性按以下层次核对，而不声称一次检查能“绝对保证”：

1. **来源可重建**：保存生成器、尺寸、深度和种子，固定 `cotengra==0.8.3`、`quimb==1.15.0`。我已用当前环境重生成六例，并逐字段比对保存的 JSON；六例均一致。现在也把该比对写入自动测试，以便以后发现版本或数据漂移。
2. **结构约束**：每个张量内指标不重复；指标集合与维度字典一致；维度为正。当前六例的维度均为 2。格点有 `行×列` 个张量、`行×(列−1)+列×(行−1)` 条内部边，输出为空，每条边出现两次。电路的开放指标数等于量子比特数，开放指标出现一次，内部指标出现两次。这些性质已在当前数据上核对，并纳入测试。
3. **路径与计分**：候选必须返回 `n−1` 次两两收缩。位置指向当步的张量列表；每步移除两项并把结果追加到末尾。非法位置、重复位置、缺步、候选异常和超时均判失败。手算小例子和独立代价计算用于交叉检查 cotengra 的结果。

这些检查证明固定文件与指定生成规则一致，并覆盖当前接口的主要错误。它们不能证明电路生成器的物理模型就是最终想研究的全部量子电路，也不能证明所有未来实例都正确。正式实验前须明确门分解、网络简化、输出量、是否允许切片，并扩展实例。当前保留集文件仍与候选程序处于同一可读工作区，**未达到严格隔离**。

## 3. 人工启发式基线

**三条基线已运行。** 第一条是 `opt_einsum.paths.greedy`；原题没有指定具体 Greedy，这只是便于复核的起点，不能把 `auto` 误当固定算法。[Greedy 算法说明](https://optimized-einsum.readthedocs.io/en/stable/greedy_path.html) 第二条是 `opt_einsum.RandomGreedy(max_repeats=32, parallel=False)`；第三条是从 Greedy 树出发，用 `cotengra.ContractionTree.simulated_anneal(seed=0, tsteps=20, numiter=20, minimize="flops")` 改进。随机相关运行另固定 `PYTHONHASHSEED=0`。三条路径均用第 1 节的评估器重新计分。

| 开发实例代价 | 格点 2×2 | 格点 2×3 | 电路 3q d1 | 电路 3q d2 |
| --- | ---: | ---: | ---: | ---: |
| Greedy | 20 | 60 | 148 | 372 |
| Random-Greedy | 20 | 52 | 144 | 364 |
| 模拟退火 | 20 | 52 | 116 | 308 |

逐例记录随项目保存在 `experiment/reports/baselines_develop.json` 和 `experiment/reports/baselines_holdout.json`。目前只记录了各方法的实际搜索耗时，尚未给它们相同预算，因此不能用这张表得出严格的算法优劣结论。正式比较还需多种子、逐例时间和更大网络。

## 4. 开源 Coding Agent 框架与下一步适配

**OpenEvolve 已接入，尚未证明它是效果最好的框架。** 我查了 [OpenEvolve](https://github.com/algorithmicsuperintelligence/openevolve)、[ShinkaEvolve](https://github.com/SakanaAI/ShinkaEvolve) 和 [CodeEvolve](https://github.com/inter-co/science-codeevolve)。OpenEvolve 提供初始程序、评估脚本、候选保存和迭代接口，且已在当前 Windows 环境完成本机模拟流程，因此先用它验证任务。其他框架的论文结果来自不同任务，不能据此推断张量网络实验的胜负。CodeEvolve 官方快速开始用 Conda 安装，没有把 Docker 列为必需条件；其平台说明指出资源监控和进程管理等功能主要按 Linux 环境设计。本机当前未用 Docker 运行。[ShinkaEvolve 论文](https://arxiv.org/abs/2509.19349) · [CodeEvolve 论文](https://arxiv.org/abs/2510.14150) · [CodeEvolve 平台说明](https://github.com/inter-co/science-codeevolve#platform-support)

本地 OpenEvolve 从提交 `15441c04bc5906790b343e0ff103d33935c33c71` 修改，补丁保存在 `../experiment/patches/openevolve.patch`。单 worker 现在会在上一轮评估后再提交下一轮；无效候选的具体错误会进入下一轮提示。本机两轮模拟已核对该反馈链。框架还支持本次兼容 API 的请求参数，以及模型生成失败时停止后续轮次。

**对“后续主要调整框架”的判断：只改框架不够。** 当前最紧急的问题是提高有效候选率，避免模型因接口不匹配而白白消耗调用。需要同时处理三个边界：

1. **候选契约**：固定 `find_path(inputs, output, sizes, seed=0)`、动态位置路径格式、允许的库及版本，并在提示中给出正确调用示例。上一轮候选向 `oe.paths.greedy` 传入不存在的 `seed` 参数，说明接口说明此前不足。
2. **分层验证与反馈**：先检查代码能否解析、导入、调用并在小网络上返回合法路径；通过后再跑全部开发实例。失败应回传具体异常和实例，不应只给一个低分。可限制自动修复次数，记录“每个有效候选消耗多少次调用和 token”。预检查能减少明显错误进入完整评估，但**不能保证模型不再写错代码，也不能避免生成调用本身的成本**。
3. **研究设置**：完善真实模型的超时、模型选择、成本记录；正式实验还须统一搜索预算和隔离测试集。这些属于实验设计和执行器，不是替换框架就能自动解决的事。

我此前还核查过本地 `autoresearch-gadgets-main`：它是研究问题目录和网站，不是可直接执行候选生成、评分与迭代的运行框架。若以后比较框架效果，应固定同一初始程序、模型、调用次数和评估预算，再比较有效候选率、最好分数及总成本。单元测试能提高正确性信心，不能证明系统“绝对正确”。

## 5. 简单 API 实验：已经跑到哪一步

**本机两轮模拟已通过；真实 API 生成过候选，但尚无有效改进。** 本机假模型完成“生成 → 执行 → 判错 → 下一轮读取错误 → 计分 → 保存报告”；独立复核与框架最佳分数一致，请求参数也进入模型请求。

真实 SiliconFlow 运行有三次关键记录：首次 `DeepSeek-V3.2` 的生成请求超时；随后 `Qwen/Qwen3.5-4B` 生成了候选代码，但它错误调用 `oe.paths.greedy`，四例开发集全失败，最佳程序仍为原始 Greedy；之后 `Qwen/Qwen3.6-27B` 的短 API 检查成功，完整生成请求却超时。运行日志和候选保存在项目的 `experiment/results/`；阶段报告位于 `张量网络/提交材料/阶段报告.md`。

现已修正提示及反馈链，并把完整生成请求设为关闭思考模式、最多 1024 个生成 token、75 秒超时、不重复请求；预检查改为短代码生成。**修改后的真实多轮运行尚未完成**。下一次验收应至少证明：真实模型产出可执行候选；每轮错误或分数可追溯；若出现无效候选，下一轮能看到具体反馈；最佳程序经独立评估仍得到相同分数。完成这一步只能证明闭环可运行，不能证明算法优于基线。

## 正式实验前仍需解决

- 锁定电路任务的物理语义、网络变换规则与资源上限。
- 扩展开发实例；将最终测试数据移出候选可读环境，避免反复查看测试结果参与选择。
- 给基线与候选相同的找路径预算；给不同框架相同的模型与调用预算。
- 用多个随机种子报告逐实例代价、搜索时间、失败率和 Agent 成本，并检查跨规模或跨拓扑表现。

当前材料是一份**最小实验的阶段报告与下一步方案**，尚不是“Agent 发现了更优收缩算法”的结论。
