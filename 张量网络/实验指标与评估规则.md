# 实验指标与评估规则

状态：最小实验规则已实现并通过小例子测试；正式比较的预算和严格测试隔离仍待完成。实现与命令见[实验目录](../experiment/README.md)。更改规则后，旧结果不能直接合并比较。

## 1. 评估对象

候选算法 `H` 接收张量网络 `G` 和随机种子，返回一条**完整的两两收缩路径** `π`。当前函数接口没有时间预算参数；执行器在外部限制每例运行时间。算法不能返回自报分数。评估器独立检查路径，再计算 `C(G, π)`。

这里的 `C` 是给定路径的**符号运算代价**，不是实际执行整个张量收缩的耗时，也不是全局最优代价。第一版统一采用 `cotengra.ContractionTree.from_path(...).contraction_cost()` 的计数约定，固定 `cotengra==0.8.3`。该接口接受指定路径，并返回收缩树的标量运算代价。不同工具可能采用不同 FLOPs 约定，数值不能直接混用。评估器先检查路径完整性，避免库的自动补全掩盖非法输出。[cotengra 路径和代价接口](https://cotengra.readthedocs.io/en/latest/autoapi/cotengra/core/index.html)


选择 cotengra 的原因是它能按指定路径重建收缩树，并统一计算标量运算代价和最大中间张量。评估器先检查路径，再调用 `from_path(..., check=True, autocomplete=False)`，不允许库自动补全路径。Greedy、其他基线和 Agent 候选使用同一计分函数；手算三张量例子和独立计数用于交叉检查。理由和限制详见[完整设计](完整设计.md)。

## 2. 主指标

对实例 `i` 和随机种子 `s`，定义相对 Greedy 代价：

`r(i,s) = C(i,s,候选算法) / C(i,Greedy)`

在固定的实例与种子集合上，主指标为这些比值的几何平均：

`R = exp(mean(log(r(i,s))))`

- `R < 1`：候选算法的总体收缩代价低于 Greedy。
- `R = 1`：与 Greedy 持平。
- `R > 1`：总体更差。

同时公布每个实例的原始代价与比值，不能只公布 `R`。OpenEvolve 需要“越大越好”的分数时，可用 `-log(R)`；这只是同一指标的变换。Greedy 只作为固定归一化参照。正式实验还要与更强基线逐项比较。

## 3. 约束与辅助指标


| 项目 | 规则 |
| --- | --- |
| 路径合法性 | 每一步引用当前存在的两个不同张量；最终恰好形成所需输出。任何实例失败，该候选本轮无有效主指标。 |
| 找路径时间 | 记录每个实例的墙钟时间；所有搜索算法使用同一上限。计时从算法开始到返回路径，不含评估器算分。 |
| 最大中间张量 | 记录路径中最大中间张量的元素数。正式比较须预先设共同上限；超过上限的路径视为不可行。所选实例的 Greedy 参照路径也须在上限内。 |
| Agent 发现成本 | 单独记录模型调用次数、tokens、评估次数和总耗时；不与路径代价混成一个分数。 |
| 随机性 | 固定并公开种子列表。随机算法在每个实例上重复运行，报告逐次结果和波动。 |

超时、异常和非法路径必须计入失败率，不能从汇总中悄悄剔除。OpenEvolve 内部可给失败候选一个固定的低分，但正式报告仍要列出失败原因和次数。

## 4. 数据使用

当前六个实例是**由现成库生成的合成网络**，不是 Agent 搜索得到的，也不是从公开基准中挑选的固定题目。格点来自 `cotengra.utils.lattice_equation`；电路来自 `quimb.tensor.circ_ansatz_1D_brickwork` 的完整态网络。生成参数和种子写入 JSON。六例已用固定版本重生成并逐字段比对，结构约束也已核对。它们只用于最小流程验证；正式比较还应加入规模更大、来源更多样的实例。

- **开发集**：用于 Agent 的生成反馈和候选选择。
- **测试集**：在候选算法和实验规则确定后评估；测试结果不返回搜索循环。测试文件应在候选执行环境之外，仅由最终评估进程读取。
- 两组实例都需保存拓扑、维度、来源、生成脚本或生成参数及随机种子。
- 若研究跨规模或跨拓扑泛化，测试集须专门包含未用于迭代的规模或拓扑；仅更换随机种子不能支持该结论。

小规模原型可以先用少量固定实例验证流程。它只能证明评估器和循环可运行，不能证明泛化。

## 5. 评估器验收

1. 对已知小网络，手工列出至少两条路径并计算预期代价。
2. 对小规模网络穷举合法路径，确认评估器对每条路径的代价与独立计算一致。
3. 检查非法位置、重复收缩、缺失步骤、异常和超时。
4. 与另一工具交叉检查时，先核对两者的运算计数约定，再比较结果。

这些检查能提高可信度，但 unit test 不能证明程序“绝对正确”。正式实验还应固定评估器版本，并保存评估输入与输出。

## 6. 基线顺序

第一条基线拟用 `opt_einsum.paths.greedy`，常用入口是 `contract_path(..., optimize="greedy")`。它适合先验证路径接口；不能把默认 `auto` 当作 Greedy，因为 `auto` 会按问题规模切换策略。原始项目介绍并未指定 Greedy 的具体实现，这是本实验暂定的基线。[Greedy 算法说明](https://optimized-einsum.readthedocs.io/en/stable/greedy_path.html) · [路径 API](https://optimized-einsum.readthedocs.io/en/stable/autosummary/opt_einsum.contract_path.html)



第二条基线使用 `opt_einsum.RandomGreedy(max_repeats=32, parallel=False)`。该版本接口未提供独立 `seed` 参数；内部试验序号固定，但跨进程还需固定 `PYTHONHASHSEED=0`，否则集合遍历顺序可能改变路径。[Random-Greedy 说明](https://optimized-einsum.readthedocs.io/en/stable/random_greedy_path.html)

三条基线和 Agent 产生的路径都交给同一个 `cotengra` 评估器计分。第三条基线是从 Greedy 树出发、固定 `seed=0` 和 `tsteps=numiter=20` 的 cotengra 模拟退火。正式比较须控制相同找路径预算；目前记录的是各算法的实际耗时，不能据此直接声称 Agent 胜过人工启发式方法。

Agent 与基线的区别在于它生成并修改**搜索算法代码**，再由该代码为每个网络找路径。评估器对所有方法返回的路径执行同一检查和计分。正式比较还需统一每例找路径的时间预算，以及 Agent 的模型调用预算。
